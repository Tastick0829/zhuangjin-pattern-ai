# 系统设计方案

> 本文件回答三个问题：**为什么做这个**、**技术路线怎么定的**、**关键决策为什么这么选**。
>
> 分层细节见：数据集 [`02-dataset.md`](./02-dataset.md)、训练 [`03-training.md`](./03-training.md)、工作流 [`04-workflow.md`](./04-workflow.md)、应用 [`05-application.md`](./05-application.md)。

## 一、问题定义

### 1.1 背景

壮锦是**国家级非物质文化遗产**（壮族传统织锦工艺）。它的核心视觉资产是**几何纹样体系**：菱形嵌套、四方连续、云雷纹、蝶花母题，配以高对比的民族配色。

现实困境有两层：

| 层次 | 问题 |
| --- | --- |
| **传承层** | 传统纹样依赖师徒相授与实物留存，数字化程度低，年轻群体接触少 |
| **应用层** | 纹样要走向当代文创，需要大量「同风格、新构图」的变体，而手工绘制成本高、周期长 |

### 1.2 本项目要解决的具体问题

> **给定一张壮锦纹样参考图，如何快速产出同风格的创意变体，并预览它在文创产品上的效果？**

注意这个问题的**边界很清晰**：

- 不是「无中生有创造壮锦纹样」（那需要理解纹样的文化语义，AI 做不到）
- 是「**在给定风格锚点下做变体扩展**」
- 目标用户是**设计师**，产出是**候选方案**，不是终稿

**这个边界定了整条技术路线**——它直接决定了后面为什么选图生图、为什么不需要巨大的数据集、为什么 LoRA 容量可以压到极小。

## 二、技术路线

### 2.1 四层架构

```text
┌─────────────────────────────────────────────────────────────┐
│ 数据层  Data                                                 │
│   壮锦纹样采集 → 筛选 → BIRME 512×512 → 英文 caption 打标     │
└──────────────────────────┬──────────────────────────────────┘
                           ↓
┌─────────────────────────────────────────────────────────────┐
│ 训练层  Training                                             │
│   Flux.1-dev + kohya-ss/sd-scripts                          │
│   LoRA 微调（networks.lora_flux, dim=2, alpha=16, 20 epoch） │
└──────────────────────────┬──────────────────────────────────┘
                           ↓
┌─────────────────────────────────────────────────────────────┐
│ 编排层  Orchestration                                        │
│   ComfyUI 工作流（图生图 + LoRA + FluxGuidance）              │
│   5 套工作流 JSON，按节点 ID 参数化                            │
└──────────────────────────┬──────────────────────────────────┘
                           ↓
┌─────────────────────────────────────────────────────────────┐
│ 应用层  Application                                          │
│   Flask（上传/生成/轮询 + HMAC-SHA1 签名）                    │
│   Canvas 前端（纹样展示 + 文创产品合成）                       │
└─────────────────────────────────────────────────────────────┘
```

### 2.2 为什么是这条路线（而不是别的）

对比三种可行路线：

| 路线 | 做法 | 优点 | 缺点 | 本项目 |
| --- | --- | --- | --- | --- |
| **A. 纯提示词** | 用现成模型 + 精心设计的提示词，不训练 | 零训练成本 | 无法稳定复现特定风格；每次结果差异大 | ✗ |
| **B. LoRA 微调 + 工作流** | 小样本微调注入风格 + 工作流编排 + 应用封装 | 风格可控、成本低、可复用可 API 化 | 需要 GPU 训练；受底模能力限制 | **✓ 采用** |
| **C. 全量微调 / 从头训练** | 用大规模纹样数据集训专用模型 | 风格表达最强 | 需要海量数据与算力；小数据集上必然过拟合 | ✗ |

**选 B 的理由**：本项目的核心约束是**数据集规模小（数十张量级）**。在这个约束下：
- A 路线无法保证风格一致性（想要的是「同风格变体」，A 每次都在漂移）
- C 路线在小数据上会严重过拟合，且成本不现实
- B 用低秩适配（LoRA）在极小参数量下注入风格倾向，正好匹配小数据场景

## 三、关键技术决策

### 决策矩阵

| 决策点 | 选择 | 放弃 | 核心原因 |
| --- | --- | --- | --- |
| **底模** | Flux.1-dev | SD1.5 / SDXL | 壮锦纹样高度依赖**几何规律性**（对称、四方连续），这是 SD 系列的架构弱项；Flux 的 DiT + 双文本编码器对结构化描述理解更强 |
| **微调方式** | LoRA | 全量微调 | 小数据集下 LoRA 抑制过拟合，产出仅数十 MB，且可插拔 |
| **LoRA 容量** | `dim=2` / `alpha=16` | dim=32（曾试） | 目标是**注入风格倾向**而非让模型背下纹样；容量小 = 过拟合风险低 |
| **训练类型** | `flux-lora` + `networks.lora_flux` | `sd-lora` + `networks.lora`（曾试） | 架构必须匹配——用 SD 的注入实现训练 Flux 会效果打折 |
| **生成范式** | **图生图为主** | 纯文生图 | 壮锦有强文化语义，从零生成易产出"像民族风但不是壮锦"；参考图 = **文化锚点** |
| **编排方式** | ComfyUI 工作流 | 手写推理脚本 | 可视化调参、导出即分享、平台直接 API 化 |
| **应用形态** | Flask + Canvas | 纯前端 / 桌面应用 | 需要服务端保管密钥并调用第三方 API；前端 Canvas 足够做产品预览 |
| **引导控制** | `FluxGuidance` 独立节点 | KSampler 的 cfg | Flux 采用 distilled guidance，机制与 SD 不同 |

### 三个决策的深入说明

#### ① 为什么"图生图"是方法论上的关键选择

这是整个项目最重要的一个判断。

**纯文生图的问题**：提示词能描述"菱形嵌套、深蓝底、红黄粉配色"，但**描述不了壮锦之所以是壮锦的那种构成逻辑**。结果往往是"看起来有民族元素的图案"，而不是能通过文化审阅的壮锦纹样。

**图生图的价值**：让用户提供参考图，等于给定了一个**文化语义的锚点**。模型在 `VAEEncode` 后的潜空间基础上做 `denoise<1` 的部分去噪——保留了原图的构图逻辑与色彩关系，只重构细节。

```text
纯文生图:  噪声 ──────────────────────> 图（全靠模型理解）
图生图:    参考图 → VAEEncode → 潜变量 + 噪声 ─> 图（锚定在参考图上）
                              ↑
                        这就是"文化锚点"
```

**代价**：创新性受限（生成图会保留输入图结构）。这个代价在本项目的目标下是**可接受的**——目标是"同风格变体"，不是"原创纹样"。

#### ② 为什么把 LoRA 容量压到 dim=2

LoRA 的原理是用两个低秩矩阵近似权重更新量：

```text
ΔW = B × A        A: dim×d,  B: d×dim
参数量 ∝ dim
```

`dim=2` 意味着**极高的压缩比**。为什么敢这么压：

| 考量 | 说明 |
| --- | --- |
| 任务简单 | 只需注入"壮锦风格倾向"，不是学习全新概念 |
| 数据量小 | 数据集仅数十张，容量大必然过拟合 |
| 可叠加 | 保留在其他 LoRA 之上叠加的余地 |

`alpha=16` 配合 `dim=2`（比值 8）保证低秩矩阵的输出幅度足够。

**若风格强度不足**：`dim` 提到 8/16 是合理的下一步，但需同时监控过拟合（看生成图是否开始复现训练集原图）。

#### ③ 为什么工作流是本项目的核心技术架构

用户原话提到「核心技术架构可能更多的是在那一个 workflow 上面还有提示词」。这个判断是准确的，理由在于：

**工作流把"一次推理调用"升级为"可复用编排资产"**：

| 维度 | 手写脚本 | 工作流 |
| --- | --- | --- |
| 调参 | 改代码 → 重启 → 等出图 | 拖节点 → 即时出图 |
| 复用 | 每换流程重写一遍 | 换节点图即可 |
| 交付 | 代码 + 环境依赖 | **导出一个 JSON** |
| 服务化 | 自己封装 API | 平台直接暴露 API + 按节点 ID 覆盖参数 |

**最后一条最关键**：因为工作流支持「按节点 ID 覆盖参数」，应用层才能用同一份工作流服务所有用户请求——只改 4 个节点（KSampler / 正负提示词 / LoadImage）的输入，不用重建整图。**这让"工作流"真正变成了"服务"**。

## 四、提示词工程

提示词在两个环节承担不同职责，**这是容易被混淆但很关键的一点**：

| 环节 | 目标 | 风格 | 示例 |
| --- | --- | --- | --- |
| **训练打标** | 让模型学会"什么算壮锦" | 泛化、关键词堆叠 | `no humans, intangible cultural heritage, Zhuang brocade, geometric patterns, ...` |
| **推理提示** | 指定本次生成的构图与配色 | 具体、自然语言长描述 | `Traditional Zhuang brocade, 512x512, symmetrical geometric patterns, dark blue background, ...` |

**为什么训练要泛化**：打标过细（每张图都描述具体构图）会让模型只会复现训练集那几张。泛化标签让模型学到**风格共性**。

**为什么推理要具体**：生成时需要约束——指定的母题、配色、构图层次越明确，结果的可用性越高。

详见 [`02-dataset.md`](./02-dataset.md) 第三节与 [`04-workflow.md`](./04-workflow.md) 第二节。

## 五、研究价值与创新点

按"实际做到的"来写，不夸大：

| 价值点 | 说明 | 支撑材料 |
| --- | --- | --- |
| **端到端链路打通** | 从数据采集到 Web 应用全链路自建，不是只调一个模型 | 本仓库全部内容 |
| **小样本风格注入的可行验证** | 在数十张数据上，用 `dim=2` 的极小 LoRA 验证了风格注入可行 | [`03-training.md`](./03-training.md) |
| **工作流作为核心资产的方法** | 把生成能力封装为可视化、可复用、可 API 化的编排资产 | [`04-workflow.md`](./04-workflow.md) |
| **非遗数字化的应用范式** | "参考图 + 风格微调 + 文创预览"是一条可复制的非遗活化路径 | [`01-design.md`](./01-design.md) |
| **工程问题解决记录** | 包含架构不匹配、分辨率一致性、参数化服务化等真实工程问题的处理 | 各层文档 |

### 诚实标注的研究局限

**这些局限必须写进任何正式表述**：

1. **风格来源混杂**：训练集与测试输入同源，模型学的是"壮锦→壮锦映射"，生成结果更接近"色彩与细节的重新渲染"
2. **无量化评估**：缺少 FID / CLIP Score / 人工评分量表等客观指标
3. **数据集规模不足**：数十张样本，风格表达受限
4. **训练步数偏少**：属"可行性验证"量级而非"性能调优"量级
5. **产品合成为原型**：Canvas 矩形叠加，非真实质感渲染

**改进优先级**：① 补独立测试集与量化评估 → ② 扩充数据集 → ③ 提升 LoRA 容量并做消融 → ④ 产品合成换 inpainting/ControlNet。

## 六、工程实践记录

项目中有几个值得记录的工程问题（详见对应文档）：

| 问题 | 表现 | 处理 | 文档 |
| --- | --- | --- | --- |
| **架构不匹配** | `model_train_type` 用 `sd-lora` 却训 Flux 底模，训练能跑但效果差 | 三者（类型/注入模块/底模）统一为 Flux | [`03-training.md`](./03-training.md) 三节 |
| **分辨率三处不一致** | 数据 512 / 训练 768，被迫缩放 | 统一为 512×512 | [`03-training.md`](./03-training.md) 坑 2 |
| **推理需公网 URL** | Liblib API 不接受本地路径 | 引入图床中转 | [`05-application.md`](./05-application.md) |
| **服务端密钥管理** | 早期版本把 API 密钥硬编码在源码 | 改为环境变量注入 + 启动自检 | [`05-application.md`](./05-application.md) 4.1 |
| **工作流参数化** | 每次生成重建整份 JSON | 按节点 ID 覆盖 4 个节点 | [`04-workflow.md`](./04-workflow.md) 三节 |

> 把"走过的弯路"写进文档，是因为**工程判断力正体现在这些地方**——知道哪里会错，比知道正确做法更有价值。

## 七、后续可拓展方向

| 方向 | 具体做法 | 预期收益 |
| --- | --- | --- |
| **量化评估体系** | 构建独立测试集 + FID/CLIP Score + 人工量表 | 让结论可被验证 |
| **数据集扩充与标注升级** | 扩到 200+ 张，按母题分组差异化打标 | 支持细粒度控制（"只要菱形"） |
| **结构解耦** | 引入 ControlNet（线稿/分割）分离结构与风格 | 提升创新性 |
| **纹样语义标签体系** | 建立壮锦母题术语表并作为条件输入 | 让生成可控可解释 |
| **真实产品合成** | 用 SD inpainting / 3D 渲染替代 Canvas 叠加 | 产出可印刷效果图 |
| **本地化部署** | 自建 ComfyUI + 本地图床，去掉第三方依赖 | 可控性与稳定性 |
| **文化传承侧延伸** | 纹样知识图谱、数字化档案 | 从"应用"回到"传承" |
